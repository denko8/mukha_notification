# Smart Notes backend — этап 2, подготовка к запуску

Актуальная пошаговая инструкция: **[OPERATIONS_RU.md](OPERATIONS_RU.md)**.
Есть миграции Alembic, лимиты запросов, шаблон VPS/HTTPS, скрипты бэкапа.
Docker/PostgreSQL и восстановление ещё требуют реального прогона.

Выбран самостоятельный backend вместо ранее предложенного Firebase.
Flutter пока **не подключён**: локальное хранение и уведомления не менялись.
Не публиковать эту сборку в интернет до прохождения списка ниже.

## Что работает в API

- Email/пароль (Argon2), вход, выход с отзывом сессии, `/me`.
- Случайные bearer-сессии на 30 дней; в БД только SHA-256 токена.
- Личные заметки и семейные доски; сервер сам назначает автора.
- Список семей и участников; приглашать может только владелец.
- Случайные одноразовые приглашения на 48 часов; в БД только хэш.
- Контроль `expected_version`: конфликт = HTTP 409, без перезаписи.
- Удаление через tombstone, чтобы офлайн-клиент мог узнать об удалении.
- Лимиты размера полей, запрет неизвестных полей, пагинация списка.

Схема данных — `app/main.py`. Интерактивный контракт — `/docs`, JSON — `/openapi.json`.
Текст напоминания парсит Flutter. Сервер хранит дату, но пока не доставляет push.

## Локальный запуск с PostgreSQL (Docker Desktop на Windows)

Из PowerShell:

```powershell
cd backend
Copy-Item .env.example .env
python -c "import secrets; print(secrets.token_hex(32))"
# Открыть .env и записать полученное значение в POSTGRES_PASSWORD.
# Пароль не присылать в чат и не коммитить.
docker compose up -d --build
docker compose ps
docker compose logs --tail 100 migrate api
```

Открыть http://localhost:8000/docs. API привязан только к loopback хоста,
PostgreSQL вообще не публикует порт. Это намеренно локальная конфигурация.
Миграции применяются автоматически перед запуском API. Для старых БД без версии см. OPERATIONS_RU.md.
Не запускать `docker compose down -v`, если данные нужны: это удалит том БД.

## Тесты без Docker

Python 3.11+:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
.\.venv\Scripts\python -m pytest -q
```

Тесты изолированы в временной SQLite: права, конфликты, удаление, сессии,
срок приглашений, одноразовость, валидация. Это не проверка поведения PostgreSQL
под нагрузкой или конкурентных транзакций. Docker и PostgreSQL нужно проверить отдельно.

## Протокол для будущего Flutter-клиента

1. UUID заметки создаётся на телефоне до отправки; серверный ID тот же.
2. Локальная запись остаётся первой. Очередь операций хранится на диске.
3. Создание: PUT `/notes/{uuid}`, `expected_version: 0`.
4. Изменение: PUT с версией, полученной от сервера. Успех возвращает новую.
5. Удаление: DELETE с JSON `{ "expected_version": N }`; tombstone не удаляется
   физически в этом этапе. Пустая payload удалённой записи не содержит текста.
6. Только после ответа сервера можно подтверждать локальную операцию.
7. При 409 клиент получает удалённое состояние, сохраняет локальный черновик
   конфликта и даёт пользователю выбор. Нельзя молча перезаписывать любой вариант.
8. GET `/notes?offset=0&limit=100` возвращает доступные записи, включая tombstones.
   Пока это полный список страницами, **не стабильный инкрементальный sync-feed**.
   При параллельных изменениях обход нужно повторять; для надёжного sync нужен
   отдельный журнал изменений/курсор и согласованный снимок.
9. Ответ потерялся после PUT: повтор может дать 409. Клиент должен сравнить
   серверный результат, а не слепо повторять создание с другим UUID.
10. `family_id` — UUID доски, не локальный `isFamily`. Перенос между областями
    пока запрещён. Локальный автор `me` не отправляется как серверный автор.

Вложения и пользовательские категории пока не входят в API. Не включать
синхронизацию существующих заметок до реализации их корректного переноса.

## Обязательное до интернета / беты

- [Реализовано] Миграции Alembic; PostgreSQL-тесты и гонки добавлены; CI-шаблон находится в backend/ci/backend.yml, автоматический запуск пока не включён.
- [Частично] Базовые ограничения частоты и тела запроса добавлены;
  квоты сессий/семей/заметок и распределённая защита ещё нужны.
- HTTPS reverse proxy, firewall, секреты, обновления, мониторинг, резервные
  копии и проверенное восстановление; БД не открывать наружу.
- Подтверждение email, восстановление доступа, удаление аккаунта.
- [Частично] Выход из семьи, удаление участника и отзыв приглашений добавлены; передача владения ещё нужна.
- Журнал синхронизации, idempotency keys, правила конфликтов, offline-очередь
  Flutter, безопасное хранение сессии (не обычный JSON настроек).
- Хранилище вложений с авторизацией и ограничениями размера/типа.
- CORS только для разрешённого web-origin, если будем подключать web.
- Push: устройства/токены, политика недублирования локальных напоминаний.
- Политика приватности, согласие на облако и выбор региона хранения.
- Dependency/security audit перед публикацией и тестирование резервных копий.

## Будущий VPS

Для небольшой закрытой беты ориентир: Linux VPS, 2 vCPU, 2–4 GB RAM,
SSD от 20–40 GB (фото быстро увеличивают объём), домен для HTTPS.
Это начальная оценка, а не гарантия вместимости. Регион хранения выбрать
с учётом аудитории и требований к персональным данным. Сервер пока можно
не арендовать. Добавлен отдельный кандидат `compose.vps.yaml`; он ещё требует проверки
по OPERATIONS_RU.md. Локальный Compose не выставляет сервис в интернет.

### CI-шаблон

Файл `backend/ci/backend.yml` подготовлен для GitHub Actions: SQLite + PostgreSQL,
Docker build, запуск API и проверка Caddy. Он пока **не активен**: подключение
GitHub в этой сессии не имеет разрешения менять workflows. Для включения владелец
репозитория может перенести файл в `.github/workflows/backend.yml` через GitHub.
Пароли из шаблона — только для одноразовых CI-баз, не использовать их на VPS.
