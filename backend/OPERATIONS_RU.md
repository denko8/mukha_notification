# Запуск и эксплуатация — этап 2

Это **кандидат для закрытого тестирования**, не заявление о готовности к открытому релизу.
Flutter пока не подключён. Работающие API не означают готовую облачную синхронизацию.

## 1. Первый запуск на Windows (Docker Desktop)

Из корня репозитория, PowerShell:

```powershell
git pull origin arena/7dad4150-mukha-notification
cd backend
Copy-Item .env.example .env
python -c "import secrets; print(secrets.token_hex(32))"
# В .env записать результат в POSTGRES_PASSWORD. Другие поля для локального запуска не нужны.
docker compose up -d --build
docker compose ps
docker compose logs --tail 100 migrate api
Invoke-RestMethod http://localhost:8000/ready
```

Миграции применяет отдельный контейнер `migrate` до запуска API.
Открыть http://localhost:8000/docs и проверить регистрацию, вход, семью, заметки.
В Authorize вставить только `access_token`, без кавычек. Не присылать токен в чат.
В API `reminder_at` передавать с часовым поясом, например `2026-11-01T14:00:00+03:00`.

### Если уже запускал старый `app.init_db`

Раньше он создавал таблицы без версии Alembic. Новый init_db запускает миграции.
На старой БД первая миграция завершится ошибкой «table already exists» — это
преднамеренно безопаснее, чем автоматически угадать схему и изменить данные.
Не удалять том и не делать `alembic stamp head` наугад. Сначала резервная копия
и сверка схемы; после проверки соответствия исходной миграции возможен
`alembic stamp 0001`, затем `alembic upgrade head`. Для пустой ненужной тестовой
БД допустимо начать заново, но удаление тома уничтожает все данные.

## 2. VPS: подготовка

Ориентир для закрытого теста: Linux, 2 vCPU, RAM 2–4 GB, SSD от 20–40 GB.
Сначала выбрать регион хранения персональных данных и домен вида api.мойдомен.

- Установить Docker Engine + Compose plugin из официальной документации.
- Настроить SSH по ключу, обновления ОС и firewall.
- Публично нужны 80/443 и ограниченный административный SSH.
- DNS A/AAAA должны указывать на сервер. Не оставлять неверную AAAA-запись.
- Скопировать код через Git; `.env` создать только на сервере, права `chmod 600 .env`.
- В `.env`: случайный hex POSTGRES_PASSWORD, API_DOMAIN (без https://), ACME_EMAIL.
- Не менять POSTGRES_PASSWORD в .env без реальной смены пароля внутри PostgreSQL:
  переменная инициализирует пароль только при создании пустого тома.

```bash
cd backend
docker compose -f compose.vps.yaml up -d --build
docker compose -f compose.vps.yaml ps
docker compose -f compose.vps.yaml logs --tail 100 migrate api caddy
curl --fail https://ВАШ_API_DOMAIN/ready
```

Caddy автоматически получает TLS-сертификат; это требует корректного DNS и
доступности ACME по сети. Наружу не опубликованы ни БД, ни API. Документация API
закрыта на прокси VPS, но доступна локально. Данные PostgreSQL и TLS — в томах.
`compose.vps.yaml` запускается **самостоятельно**, а не вместе с compose.yaml.

**Пока не приглашать реальных пользователей без проверки списка в конце.**

## 3. Обновление

1. Снять резервную копию, проверить её вне рабочего тома.
2. Зафиксировать текущий Git commit и версии образов.
3. Скачать изменения.
4. На этом раннем этапе использовать короткое окно обслуживания:

```bash
docker compose -f compose.vps.yaml stop api caddy
docker compose -f compose.vps.yaml build api migrate
docker compose -f compose.vps.yaml run --rm migrate
docker compose -f compose.vps.yaml up -d api caddy
```

При ошибке миграции не выполнять downgrade автоматически. Проверить логи,
схему, совместимость предыдущей версии и резервную копию. Деструктивные
миграции требуют отдельного плана. `docker compose down -v` удаляет данные!

## 4. Резервные копии

Из каталога backend/ на VPS:

```bash
bash scripts/backup.sh
bash scripts/restore-check.sh backups/ИМЯ.dump
```

Первый скрипт пишет pg_dump в custom-формате, с приватными правами и атомарным
переименованием. Второй восстанавливает в **отдельную временную БД**, проверяет
таблицы и удаляет только её. Рабочая БД не перезаписывается.

Настроить ежедневный cron, мониторинг ошибок и свободного места, срок хранения.
Копии содержат заметки и хэши паролей: шифровать, выносить на отдельное хранилище,
ограничить доступ. Копия на том же VPS не спасает от потери VPS.
Эти скрипты ещё нужно реально проверить с Docker/PostgreSQL.

Очистка истёкших сессий/приглашений (например, ежедневно):

```bash
docker compose -f compose.vps.yaml exec -T api python -m app.cleanup
```

Tombstone заметок не удаляем: нельзя потерять сведения об удалении для офлайн-клиентов.

## 5. Ограничения и гарантии

- Запрос: не более 128 KiB фактического тела, ожидание тела до 15 секунд.
- На socket IP: 20 запросов/мин к авторизации/инвайтам, 300 остальных.
- Лимитер хранит максимум 10 000 ключей, после заполнения отказывает новым.
- Лимитер **в памяти одного процесса**, перезапуск сбрасывает счётчики.
- За Caddy все запросы приходят от одного IP: лимит становится общим для VPS.
  Это консервативная защита для маленького теста. Для масштаба нужны доверенная
  конфигурация прокси, rate limiting по IP + аккаунту и общий Redis/edge-limiter.
- Не включать несколько workers/реплик без пересмотра лимитера.
- X-Forwarded-For от публичного клиента не используется для обхода лимитов.
- /health — процесс жив, /ready — есть доступ к таблице users. Это не проверка
  всех зависимостей и не полноценный мониторинг миграций/диска/бэкапов.
- Выход участника отбирает дальнейший доступ на сервере, но не может стереть
  ранее скачанные данные на чужом телефоне. Клиентскую очистку ещё реализуем.
- Удаление участника и запись семейной заметки сериализованы блокировкой семьи
  в PostgreSQL. SQLite не доказывает корректность row-level locking.
- Есть согласованные полные снимки и квитанции операций (SYNC_PROTOCOL_RU.md).
  Инкрементального журнала, вложений и подключения Flutter пока нет.

### CI-шаблон

Файл `backend/ci/backend.yml` подготовлен для GitHub Actions: SQLite + PostgreSQL,
Docker build, запуск API и проверка Caddy. Он пока **не активен**: подключение
GitHub в этой сессии не имеет разрешения менять workflows. Для включения владелец
репозитория может перенести файл в `.github/workflows/backend.yml` через GitHub.
Пароли из шаблона — только для одноразовых CI-баз, не использовать их на VPS.
