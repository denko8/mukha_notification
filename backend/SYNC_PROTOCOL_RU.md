# Протокол синхронизации v1 — серверный этап

Реализован **полный согласованный снимок**, а не инкрементальный журнал изменений.
Это осознанный вариант для небольшой закрытой беты. Клиентская очередь Flutter
ещё не подключена. Нельзя включать старый markSynced для всех заметок после одного запроса.

## 1. Отправка: durable idempotency

Для каждого отдельного PUT/DELETE заметки клиент создаёт UUID операции и сохраняет
**до сети** вместе с неизменяемым запросом в локальной очереди. UUID заметки тоже
создаётся на телефоне заранее. Все запросы авторизованы bearer-сессией.

```http
PUT /notes/00000000-0000-0000-0000-000000000001
Authorization: Bearer <session>
Idempotency-Key: 11111111-1111-1111-1111-111111111111
Content-Type: application/json

{"expected_version":0,"text":"Забрать заказ","family_id":null}
```

- expected_version=0 — создание, N>0 — изменение известной версии.
- Сервер фиксирует изменение и квитанцию операции **одной транзакцией**.
- Повтор с тем же ключом и запросом возвращает исходный ответ (HTTP 200),
  даже если заметку после этого изменило другое устройство.
- Тот же ключ с другим телом/методом/ID заметки — 409. Новый текст — новая операция.
- Ключи привязаны к аккаунту. Квитанция не позволяет обойти отзыв семейного доступа.
- Ключ необязателен для обратной совместимости старых вызовов API, но **обязателен
  по контракту будущей клиентской очереди**.
- Квитанции сохраняются в PostgreSQL и переживают перезапуск API. Они не истекают
  автоматически: иначе повтор старой операции мог бы неожиданно изменить данные.
- Начальная квота — 10 000 квитанций на аккаунт. При достижении сервер вернёт 429,
  а не начнёт молча удалять историю. Ротация требует протокола подтверждений устройств.
- Квитанции содержат исходный ответ, в том числе текст: удаление заметки пока не
  означает стирание всех её исторических копий. Политика удаления аккаунта и retention
  должна быть завершена до реальных пользовательских данных.

DELETE использует тот же механизм, с телом `{ "expected_version": N }`.
`GET /notes/{uuid}` возвращает текущее состояние/отметку удаления для разбора конфликта.

### Ошибки и подтверждение локальной очереди

- Сетевой сбой / 5xx: оставить запрос в очереди; повторить с **тем же ключом и телом**,
  с backoff+jitter. Таймаут не означает, что операция не выполнена.
- 401: остановить очередь, запросить повторный вход; данные не удалять.
- 404: возможно отозван доступ; перепроверить список семей, не повторять бесконечно.
- 409 версии: получить текущую заметку, сохранить обе версии; не выбирать победителя
  по времени телефона. Если пользователь выбрал свою версию, новый ключ + новая версия.
- 422: ошибка запроса, не повторять автоматически.
- 429: соблюдать Retry-After, если он есть; для квот показать причину пользователю.
- Успех: подтвердить **только эту операцию**. Если за время запроса пользователь изменил
  текст, новая локальная ревизия остаётся pending. Старый ответ её не перезаписывает.
- Не делать два одновременных запроса одной заметки: следующий зависит от версии предыдущего.
- Не менять аккаунт у уже сохранённой операции. Очереди/версии/снимки изолировать по user_id.

## 2. Скачивание: immutable snapshots

1. POST `/sync/snapshots` → `snapshot_id`, `expires_at`, `total`, `family_ids`.
2. GET `/sync/snapshots/{id}?offset=0&limit=100` → `notes`, `next_offset`, `total`.
3. Продолжать с **next_offset**, пока он не null.
4. Повторно проверить GET того же снимка перед локальной фиксацией (полномочия/TTL).
5. Применить подготовленный набор в одной локальной транзакции; затем освободить
   снимок DELETE `/sync/snapshots/{id}`. Сбой освобождения не отменяет применение.

Состав заметок, порядок, версии и текст заморожены при создании. Новые правки не
сдвигают страницы. Следующий цикл создаёт новый снимок и получает изменения.
Снимок включает tombstones; удалённая payload очищена. Каждая запись имеет серверную
версию и author_id. Семейные записи имеют конкретный family_id.

- По умолчанию 100, максимум 200 записей на страницу.
- TTL 10 минут, максимум 3 активных снимка на аккаунт.
- Максимум 1000 заметок (включая tombstones) и 8 MiB JSON на снимок.
- При превышении лимитов — **явная ошибка 413**, не обрезанный набор с видом успеха.
- Доступен только владельцу снимка, с действующей авторизацией.
- Изменился набор семей → 409. Истёк TTL → 410. Незаконченный набор отбросить,
  создать новый снимок; действующие локальные заметки не трогать.
- Освободить собственный снимок можно даже после отзыва доступа/истечения TTL.
- Удалённый доступ нельзя гарантированно отозвать у уже загруженного на телефон
  текста: нужно объяснять это пользователю. Проверка перед фиксацией сокращает,
  но не устраняет окно конкурентного отзыва доступа.

### Правила локального применения (ещё предстоит реализовать)

- Скачивание идёт в staging, не заменяет живую ленту постранично.
- Сначала проверить полноту и согласованность snapshot_id/total/offset.
- Серверная версия меньше уже известной → не откатывать локальные данные.
- Новая локальная правка/pending операция всегда сохраняется до разрешения конфликта.
- Отсутствие записи в снимке само по себе **не команда удалить личный черновик**.
- Отозванные семейные области удаляются из активного кэша; несохранённые личные
  правки не публикуются обратно в семью без полномочий.
- Первая привязка локального `me`/isFamily к аккаунту требует явного выбора,
  а не массовой автоматической загрузки на произвольную семейную доску.
- Вложения пока не поддержаны API. Синхронизацию заметок с вложениями нельзя
  выдавать за полную до реализации загрузки файлов и их прав доступа.

## 3. Масштабирование и проверки

Снимки хранят полный JSON в БД, это не решение для десятков тысяч заметок на человека.
Для роста нужен журнал изменений с устойчивым курсором и согласованной фиксацией
транзакций: обычный автоинкремент ID может пропустить поздно закоммиченную запись.

PostgreSQL — поддерживаемая БД развёртывания. Персональная строковая блокировка
сериализует повторы одного пользователя; условные обновления защищают семейные версии.
SQLite — только быстрые тесты, не гарантия такого же поведения блокировок.

Покрыты тестами: повторы PUT/DELETE, смена тела при том же ключе, исторический ответ,
страницы при вставках/удалениях, изоляция снимков, TTL/квоты, отзыв доступа. Тест гонки
идемпотентных повторов включается с TEST_POSTGRES_URL; локально без PG он пропускается.
Прогон Docker/PostgreSQL всё ещё обязателен до подключения реальных данных.
