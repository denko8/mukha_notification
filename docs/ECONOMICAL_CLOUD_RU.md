# Экономичная схема: небольшой VPS + приватное S3-хранилище

Актуальный этап. Предыдущие документы про BYTEA/полные снимки описывают прошлую версию.
Новая миграция backend — **0005**, клиентская SQLite — v4.

## Что бесплатно, за что можно брать оплату

- Основная офлайн-лента остаётся локальной. Ничего из неё не загружается автоматически.
- Текстовые заметки облачного раздела и семейные права работают без файлового тарифа.
- «Только на устройстве»: вложение сохраняется в приватный каталог телефона и таблицу
  локальных файлов. Оно НЕ попадает в upload queue, не требует запроса тарифа, не передаётся
  родственникам и не восстановится из облака после удаления приложения/потери телефона.
- «Облачная копия»: явное согласие при прикреплении. Требует действующего серверного
  тарифа. В тестовой реализации — 1 ГиБ на загрузившего пользователя, файл до 5 МиБ,
  заметка до 20 МиБ и 10 файлов. Бесплатная файловая квота — 0.
- Участники семьи читают общие облачные файлы без многократного физического копирования;
  место считается загрузившему пользователю. Его тариф не оплачивается всеми участниками.
- По истечении тарифа новые загрузки блокируются, ранее загруженное не стирается.
  Повтор уже принятой загрузки не считается новой и не расходует место повторно.
- Реального checkout/автосписания пока НЕТ. Старое обещание «безлимитных вложений» и
  фиктивное включение пробного периода убраны из экрана тарифов. Цена и канал оплаты
  требуют отдельного решения. Локальный proEnabled не выдаёт облачное право.

### Активация только администратором для тестов

После регистрации аккаунта и настройки S3, на сервере (не через API телефона):

```bash
docker compose exec api python -m app.cloud_admin plan --email USER_EMAIL --tier cloud --days 30
```

Для VPS добавлять `-f compose.vps.yaml` к docker compose. Возврат на free аналогично.
Это ручное тестовое право, **не подтверждение оплаты**. Будущий платёжный webhook
должен проверять подпись провайдера, повторяемость событий и привязку к user_id.
Не продавать этот доступ до подключения платежей, условий и политики возвратов.

## 1. Изменения вместо полных снимков

GET `/sync/changes?cursor=...&limit=100` возвращает только изменённые записи и tombstones.
Первая загрузка/смена семейных прав — bootstrap страницами; затем клиент хранит курсор.
Курсор привязан подписью к аккаунту, текущему набору семей и сроку 30 дней.
На смену семей/истечение курсора/откат БД — явный sync_reset и bootstrap.

На сервере `note_changes` — **одна компактная строка на заметку**, не история всех текстов.
Новая правка переносит позицию этой строки вперёд. При повторной правке во время обхода
заметка может прийти ещё раз, но не должна пропасть позади курсора.

`sync_clock` блокируется последним при публикации изменения и удерживается до commit.
Страница чтения удерживает ту же блокировку, не берёт затем семейные/user locks.
Это предотвращает пропуск поздно закоммиченной записи с меньшим номером.
Для небольшого VPS это простая корректная сериализация, **не бесконечная горизонтальная
масштабируемость**. Нагрузку и блокировки PostgreSQL нужно измерить отдельно.

Клиент фиксирует страницу и курсор одной SQLite-транзакцией, сохраняет pending/конфликты,
не откатывает более высокие версии. Bootstrap сначала собирается полностью; отозванные
семейные области убираются сразу после получения актуальных прав, даже если далее сеть упала.
Первый bootstrap ограничен 100 страницами в клиенте; более крупные коллекции требуют
расширения/стейджинга на диске, не обещаем их поддержку на текущем этапе.

Новые mutation receipts не дублируют исторический текст: при повторе точное тело запроса
проверяется хэшем, текст ответа восстанавливается из него. Старые квитанции не удаляются
автоматически. Tombstones и квитанции пока имеют собственный долгосрочный объём — безопасное
протокольное подтверждение удаления устройствами остаётся следующим этапом.

## 2. Приватное объектное хранилище

В `.env` заполнить S3_ENDPOINT_URL (HTTPS), S3_REGION, S3_BUCKET,
S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY. Секреты — только на сервере, не в Flutter и не в чате.
Нужен отдельный приватный bucket и ключ с правами только для него (Put/Get/Delete).
Никакого public-read, публичного list и бессрочных ссылок.

API в compose.vps.yaml получил outbound-сеть для доступа к удалённому S3; портов API/БД
наружу по-прежнему нет. Миграции не обращаются к S3 и не требуют ключей.
Без S3 текстовая синхронизация и локальные файлы доступны; облачная загрузка явно недоступна.

- Новые файлы пишутся в S3, в PostgreSQL остаются метаданные и object_key, data=NULL.
- Загрузка пока проходит через API (ограниченная память/размер), повторяется тем же ID.
  Следующий масштабный этап — presigned PUT с reservation/подтверждением квот.
- Скачивание: API проверяет права и выдаёт подписанный URL на 60 секунд.
  Телефон скачивает прямо из S3, не отправляя ему bearer-токен API; проверяет SHA-256.
- Выданная ссылка может работать до истечения 60 секунд даже после отзыва доступа.
  Это сознательное ограничение короткоживущих ссылок. После истечения требуется новая проверка.
- Скачивание оригинала не запускается синхронизацией: только нажатием пользователя.
- Проверенный кэш повторно открывается без сети. Цель автоматического кэша — до 100 МиБ
  на аккаунт/сервер, старые незакреплённые копии очищаются по last-used. local-* и upload-*
  никогда не удаляются как кэш. Локальные файлы пользователь удаляет явно с подтверждением.
- Скачанные/локальные копии нельзя гарантированно отозвать с чужого телефона.
- Подпись типа файла не является AV-сканированием; перед публичным запуском нужен карантин/AV.

### Старые BYTEA-файлы

Миграция 0005 НЕ удаляет их. После настройки bucket:

```bash
docker compose exec api python -m app.cloud_admin migrate-blobs
```

Каждый файл читается обратно из S3 с проверкой SHA-256; только затем обнуляются байты в БД.
Миграцию можно повторить. Старый download через API оставлен для ещё не перенесённых файлов.
После переноса pg_dump больше не содержит все оригиналы. **Нужен backup и bucket тоже.**
Downgrade 0005 откажется работать, пока есть external-only вложения: не теряем данные молча.

### Удаление объектов и резервные копии

Удаление заметки/файла записывает object_garbage в ту же БД-транзакцию.
Сборщик повторяемо удаляет объект и только затем задание:

```bash
docker compose exec api python -m app.cloud_admin collect-objects
```

Запускать по расписанию, контролировать ошибки. Логическая квота освобождается при удалении
метаданных; физическое место освобождается сборщиком, а при bucket versioning — по lifecycle.
Сбой после PUT, но до DB commit может оставить непривязанный объект: требуется inventory/
сверка и осторожный GC с grace period. Автоматическое массовое удаление таких объектов
пока НЕ включено, чтобы не снести незавершённую загрузку.

Настроить versioning/backup bucket, lifecycle старых версий и восстановление вместе с БД.
Не считать postgres backup достаточным. Не включать blind expiration всех originals:
это уничтожит единственную облачную копию. Для просроченных подписок политика хранения,
предупреждения и согласие ещё должны быть определены; автоматического удаления сейчас нет.

## 3. Метрики и замеры

GET `/cloud/usage` показывает тариф, квоту, логически занятые активными файлами байты,
готовность S3 и счётчики uploaded_bytes / download_granted_bytes / sync_response_bytes.

Это НЕ финансовый биллинг: granted bytes не равны фактическому S3 egress (URL может
не открыться или использоваться несколько раз). Реальные расходы сверять с метриками S3,
числом GET/PUT, исходящим трафиком, версиями bucket, GC-остатками и резервными копиями.
Счётчики накопительные, не «за текущий месяц». Заголовки HTTP/TLS в них не включены.

Воспроизводимый тест, из backend/:

```bash
python -m scripts.measure_cloud --notes 20 --chars 500
python -m scripts.measure_cloud --notes 100 --chars 1000
```

Проверенный результат (UTF-8 русский текст, без файлов):

| Сценарий | Полный список, байт | Bootstrap, байт | После одной правки, байт | Без изменений, байт |
|---|---:|---:|---:|---:|
| 20 × 500 символов | 25 401 | 25 683 | 1 554 | 284 |
| 100 × 1000 символов | 227 001 | 227 284 | 2 555 | 285 |

Снижение тела ответа после одной правки: 93,88% / 98,87% относительно полного списка.
Это тест JSON response bodies через TestClient/SQLite, не замер VPS/RAM/сети/S3/нагрузки.
Индекс изменений содержит 20/100 строк, а не новую копию каждого текста на каждую правку.
Точные байты могут немного меняться при изменении метаданных/формата курсора.

## Перед выбором хостинга

1. Реальный PostgreSQL + приватный S3: повтор загрузки, ошибка сети, права, cleanup.
2. Android: flutter analyze/test, миграция SQLite, офлайн-кэш, локальный режим, WorkManager.
3. Фиксировать DAU, обменов/день, долю пользователей облачных файлов, средний размер,
   долю повторного открытия из кэша, число GET/PUT, p95 API и RAM процесса.
4. Проверить восстановление БД + bucket и нагрузку на глобальный clock lock.
5. После этих данных выбирать VPS, регион и конкретный storage-провайдер/тариф.
   Цены и обещание «выдержит N пользователей» здесь не выдумываются.

Удалённые push, платежный webhook, подтверждение email и публичная эксплуатационная
готовность этим этапом не объявляются завершёнными.

### Замер реального хранилища после подключения

```bash
docker compose exec api python -m app.cloud_admin measure-storage
```

Команда читает активные размеры вложений, остаток BYTEA, физический размер таблиц+
индексов PostgreSQL и метаданные объектов S3 (LIST, не скачивая оригиналы).
Обход ограничен 100 страницами; `complete=false` означает неполный инвентарь.
LIST тоже может тарифицироваться провайдером. Noncurrent versions/реплики в сумму
current objects не входят. После переноса BYTEA PostgreSQL может удерживать ранее
выделенные страницы для повторного использования; уменьшение файла БД требует
отдельной процедуры обслуживания, не автоматического VACUUM FULL в рабочее время.
